# Windows 虚拟桌面项目目标
> 建立独立全屏桌面，统一承载浏览器、文件管理器和查验业务界面，解决方向与显示比例不匹配问题。

更新日期：2026-10-30。

## 当前阶段与目标

当前处于需求与架构分析阶段。本次先将目标文档提交到 GitHub 的 main 分支，不实现业务代码。

项目仓库：[ChenWingYan/Cic_virtual_desktop](https://github.com/ChenWingYan/Cic_virtual_desktop)。

目标运行平台为 Windows。软件作为独立全屏虚拟桌面运行，提供三个应用入口，并在软件内部完成方向和比例校正，避免依赖 Windows 显示旋转作为解决方案。

这里的虚拟桌面是应用级桌面外壳。首期不开发虚拟显示器驱动，不替换 Windows 桌面管理器，也不要求任意外部程序都能被旋转或校正。

## 显示问题与事实基线

用户本次描述为：实体屏幕宽高比是 3:4，电脑解析到的比例是 4:3。此前项目资料记录了相反的比例，本次以当前描述作为需求基线；最终以实体屏和实际输出链路校准结果为准。

用户反馈 Windows 旋转后，系统比例也会变化，因此希望在软件内部选择方向并校正显示。

具体系统分辨率、Windows 缩放比例、屏幕原生像素尺寸、显示器缩放模式、连接链路和输入方式尚待确认。不能只根据 3:4 与 4:3 推定补偿系数，也不能只根据电脑截图认定实体屏显示正常。

目标效果包括：中文和英文字体形状正常，圆形不变成椭圆，图片及视频比例正确，按钮和点击区域一致。方向校正、界面布局、字体大小与实体屏比例补偿是不同职责，需要分别处理。

## 首期功能范围

| 模块 | 目标 | 边界 |
| --- | --- | --- |
| 虚拟桌面 | 全屏主页、三个应用入口、应用切换、显示设置、退出入口 | 不要求复刻完整 Windows 桌面 |
| 浏览器 | 加载网页、地址栏、前进、后退、刷新及基本输入 | 网页内容与浏览器工具栏都需要接入显示校正 |
| 文件管理器 | 显示目录和文件、进入目录、返回上级、刷新 | 自建界面；复制、移动、删除和文件预览等操作后续明确 |
| 查验业务入口 | 打开并使用指定业务软件的界面 | 优先接入现有前端和后端服务，具体兼容方式需要验证 |
| 显示设置 | 选择 0°、90°、180°、270°，配置比例补偿和字体大小，保存设置 | 只改变受本软件管理的内容，不修改 Windows 的显示方向 |

文件管理器调用外部程序打开文件时，外部窗口不会自动获得本软件的显示校正。需要保持校正的预览或操作，应在受管理界面内实现。

## 架构方向与职责

参考业务工程：`E:/Maxvision/Project/CustomInspectCounter_NewTypeDemo`。

沿用其 Electron JavaScript、Vite TypeScript、C++20 分层思路，在本项目建立虚拟桌面外壳。保留业务软件的独立后端职责，不把设备及业务逻辑复制到桌面模块中。

| 层次 | 职责 |
| --- | --- |
| Electron 外壳 | 窗口管理、应用生命周期、本机文件访问接口、配置保存及业务进程接入 |
| Vite TypeScript 界面 | 桌面主页、应用切换、文件管理器、浏览器工具栏及显示设置 |
| 应用内容 | 业务前端页面和浏览器网页；内容的显示与输入接入统一校正接口 |
| 显示校正 | 管理逻辑画布、旋转、比例补偿、输出位置和输入坐标换算 |
| C++20 能力与业务后端 | 复用现有业务服务；新增原生渲染或系统能力是否需要 C++20，由原型验证决定 |

本机文件和进程能力通过受控接口提供。外部网页不直接获得 Node.js、本机文件或业务控制权限。

“叠一层虚拟桌面”表示由外壳管理应用入口及内容呈现。仅启动一个独立业务 EXE，然后在其上覆盖桌面页面，不能自动修正该 EXE 的字体和画面。

## 业务工程的已知显示行为

以下事实来自本轮静态源码核对，不代表已验证其在目标实体屏上的运行效果。

- `app-shell/package.json`：Electron JavaScript 外壳入口为 `src/main/index.js`。
- `web-ui/package.json`：前端采用 Vite 和 TypeScript。
- `cpp-core/CMakeLists.txt`：C++ 标准设为 C++20。
- `app-shell/src/main/cppCoreProcess.js` 的 `createCppCoreProcessManager`：管理业务后端进程。
- `web-ui/src/main.ts` 的 `updateMainInspectionCanvasScale`：主业务画布以 1920×1080 为基准，分别计算横纵缩放比例；两者不同时会改变内容形状。
- 同文件的 `updateSecondaryInspectionCanvasScale`：副屏采用等比缩放。
- `app-shell/src/main/index.js` 的 `ensureBrowserViewAttached`、`applyBrowserViewport`：现有网页通过独立 BrowserView 呈现，按矩形设置位置和大小。

接入业务前端时，需要梳理现有布局缩放，避免业务页面与虚拟桌面重复补偿。既有 1920×1080 布局能否在目标逻辑画布上保持可读、是否需要布局适配，应结合样机验证。

现有业务页面还依赖 Electron preload 和运行配置。不能只加载一个页面地址，就视为业务功能已完整接入。主副屏支持、后端启动归属及退出行为也需要在集成阶段明确。

## 统一显示校正要求

1. 统一定义逻辑画布和输出区域。90° 与 270° 时正确处理宽高交换和布局边界。
2. 明确变换顺序：内容布局、方向旋转、实体屏比例补偿和输出定位。
3. 内容布局优先保持比例，必要时留边或调整布局；实体屏补偿可以使用横纵不同的系数，以抵消设备造成的拉伸。
4. 字体大小独立设置。调整字号不能替代比例补偿；几何比例恢复也不等于恢复已经损失的清晰度。
5. 桌面、工具栏、业务页面、网页内容及软件内弹窗使用一致的方向和补偿参数。
6. 输入与输出采用相互对应的坐标变换，覆盖点击、滚轮、拖拽和实际使用的触摸操作。
7. 显示设置持久化，重启后恢复。原型阶段提供恢复默认显示的操作入口。

浏览器网页由独立渲染内容承载，不能假设桌面根节点的 CSS transform 会同时作用于网页。仅更换 BrowserView 为其他嵌入视图，也不代表已经解决统一旋转。

可验证的技术路线之一是：离屏渲染网页或业务内容，将画面交给统一显示层，再将输入换算回原内容坐标。最终选择需要验证性能、清晰度、中文输入、焦点、弹窗和视频效果，不在需求阶段锁定具体渲染实现。

参考：[Electron 离屏渲染说明](https://www.electronjs.org/docs/latest/tutorial/offscreen-rendering)。

Windows 原生文件对话框、系统菜单和输入法候选窗口不属于普通网页画布。需要逐项验证，明确保留、替代或适配方式，不能默认它们自动接受校正。

## 分阶段实施建议

| 阶段 | 工作内容 | 完成条件 |
| --- | --- | --- |
| 目标基线 | 整理目标、架构方向和未决事项 | 文档进入 main，保留待验证边界 |
| 桌面原型 | 建立 Electron 外壳、桌面主页、三个入口、设置和校准页 | 外壳可以启动，方向设置可切换，统一校正接口明确 |
| 显示与浏览器验证 | 接入真实网页，验证旋转、补偿及输入；补齐基本文件浏览 | 实体屏上的中文、圆形、网页和点击位置通过验证 |
| 业务集成 | 接入业务前端与 C++20 后端，梳理旧缩放逻辑及 preload 依赖 | 核心业务界面能显示、能操作，且不产生重复拉伸 |
| 运行完善 | 配置持久化、退出恢复、打包及必要的性能优化 | 可在目标 Windows 设备安装和使用 |

可以先搭桌面和浏览器，再完善显示效果；但统一显示校正接口和浏览器渲染边界应从原型阶段预留。

## 验收标准

- 在目标 Windows 设备上启动全屏桌面，三个入口可进入对应界面并返回桌面。
- 四种方向下，画面位置正确，没有关键内容被裁切；需要留边时表现明确。
- 校准页包含中文、英文、圆形、方格和四角点击目标，在实体屏上检查形状、清晰度和命中位置。
- 浏览器实际网页与工具栏方向一致；导航、输入、滚动和焦点正常。中文输入法及网页弹窗需专项验证。
- 文件目录可以浏览和刷新；执行文件操作时符合最终确认的操作范围。
- 业务软件界面与桌面采用一致的校正参数，文字、图片和视频不因重复缩放产生额外变形。
- 修改并保存显示设置后，重启程序可以恢复；能够恢复到可操作的默认显示。
- 留存软件截图与实体屏照片或视频。截图只能证明软件输出，不能独立证明物理显示效果。

以上均为验收目标，当前尚未完成运行验证或现场验证。

## 待确认事项

- 实体屏原生像素尺寸、安装方向、显示器缩放模式及连接设备是否额外旋转或缩放。
- Windows 具体分辨率、缩放比例、系统版本及目标机器性能。
- 浏览器面向固定网站还是任意网页，是否需要下载、上传、视频及多标签。
- 文件管理器需要的文件操作、允许访问的目录及预览类型。
- 业务软件采用前端接入还是保留独立进程显示；现有 preload 接口如何兼容。
- 业务主副屏是否都要纳入虚拟桌面，后端由谁启动和停止。
- 实际使用鼠标、键盘还是触摸屏，系统输入法和原生对话框如何呈现。

这些事项不阻碍记录目标，但会影响后续实现和现场验收。
